# Контракт API и проверка системы

## Транспорт и маршруты

Базовый адрес при запуске через Compose — `http://localhost:9000`. Маршруты заданы
без завершающего `/`, `APPEND_SLASH=False`; вариант со слешем не является тем же маршрутом.
API не требует аутентификации. Ответы представлений формируются в JSON.

POST и DELETE читают тело запроса и дополняют отсутствующие поля query-параметрами.
При совпадении ключей приоритет имеет тело. GET читает только query-параметры.
Настроены парсеры JSON, `application/x-www-form-urlencoded` и `multipart/form-data`.
JSON-тело должно быть объектом.

| Метод и путь | Входные поля | Успешный ответ |
|---|---|---|
| `POST /rooms/create` | Обязательные `description`, `price` | `201`, `{"room_id": 1}` |
| `DELETE /rooms/delete` | Обязательный `room_id` | `200`, `{"deleted": true}` |
| `GET /rooms/list` | Необязательные `sort_by`, `order` | `200`, массив номеров |
| `POST /bookings/create` | Обязательные `room_id`, `date_start`, `date_end` | `201`, `{"booking_id": 1}` |
| `DELETE /bookings/delete` | Обязательный `booking_id` | `200`, `{"deleted": true}` |
| `GET /bookings/list` | Обязательный `room_id` | `200`, массив броней номера |

Идентификаторы во входных данных должны быть положительными целыми числами.
`sort_by`: `created_at` (по умолчанию) или `price`; `order`: `asc` (по умолчанию)
или `desc`. Правила полей и связей приведены в [структурной модели](structural-model.md).

Пример элемента списка номеров:

```json
{
  "room_id": 1,
  "description": "Двухместный номер",
  "price": "149.90",
  "created_at": "2030-01-15T10:30:00Z"
}
```

Пример элемента списка броней:

```json
{
  "booking_id": 1,
  "date_start": "2031-06-20",
  "date_end": "2031-06-25"
}
```

Списки возвращаются без обёртки и пагинации. Для существующего номера без броней
результат равен `[]`; для несуществующего номера возвращается `404`.
Примеры HTTP-команд приведены в [основном README](../README.md).

## Ошибки

Формат прикладной ошибки — объект с одной строкой `error`:

```json
{"error": "Room with id 42 was not found"}
```

| Код | Причина |
|---|---|
| `400` | Отсутствующее или недопустимое поле, неверный JSON или тело не в виде объекта |
| `404` | Номер/бронь не найдены, либо URL не существует |
| `405` | Неподдерживаемый HTTP-метод для известного маршрута |
| `406` | Заголовок `Accept` не допускает доступное JSON-представление |
| `409` | Пересечение дат бронирования при включённой проверке |
| `415` | Неподдерживаемый тип содержимого при разборе тела запроса |
| `500` | Непредвиденная внутренняя ошибка |

При нескольких ошибках валидации возвращается первая. Для ошибки поля к сообщению
добавляется имя поля; общая ошибка сериализатора возвращается без такого префикса.
Доменные сообщения: `Room with id {id} was not found`,
`Booking with id {id} was not found`, `Room is already booked for the requested dates`.
Неизвестный URL возвращает `Not found`.

Единый обработчик покрывает ошибки DRF-представлений. Для уровня Django отдельно
заданы JSON-обработчики 404/500; поведение вне представлений также зависит от режима
отладки. Ошибки инфраструктуры до попадания запроса в Django не входят в этот контракт.

## Запуск проверок

В настроенном окружении с `.env`, Poetry и доступным PostgreSQL:

```bash
poetry install --with dev
docker compose up -d db
poetry run pytest
poetry run python src/manage.py makemigrations --check --dry-run
```

Тесты БД используют отдельную тестовую базу pytest-django. `make check` дополнительно
запускает проверку зависимостей, Ruff, mypy, Bandit и отчёты Radon.
[GitHub Actions](../.github/workflows/ci.yml) использует Python 3.12 и PostgreSQL 17,
проверяет Ruff, отсутствие недостающих миграций и выполняет pytest с покрытием.
Наличие этих проверок в конфигурации не означает, что они запускались при подготовке
данной документации.
